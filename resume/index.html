自傳

專業背景與跨域整合

我是陳政瑋，具備約四年 Java 軟體開發經驗，以後端開發為核心，亦具 React／Redux、JavaScript、JSP 等前端經驗。曾參與保險核心系統、AI／真人客服及企業級微服務專案，熟悉從需求分析、開發、整合、測試到部署維運的完整流程。隨著實務經驗累積，我逐步由功能開發延伸至系統架構、技術決策及工程品質改善，近期更於富邦人壽核心系統現代化專案中承擔技術領導、工程治理及交付管理等職責。

進入軟體產業之前，我累積約八年建築設計與大型工程整合經驗，曾參與桃園機場第三航廈等公共工程，負責建築、結構、機電的跨專業介面協調與設計整合。工作期間，我透過 Dynamo 與 Python 自動化處理 BIM 資料，因而對程式開發產生興趣，並於完成緯育 Tibame Java 專業培訓後正式轉職。雖然建築與軟體屬於不同領域，但過去的工程經驗讓我養成從整體目標出發，分析需求、功能分區、介面及相依關係的習慣，這也成為日後進行系統設計與跨團隊協作的重要基礎。

企業系統開發與設計實務

於松凌科技期間，我參與保險核心系統開發與維護，使用 Java、Spring Boot、Spring Cloud、Spring Batch、Oracle DB、React／Redux 等技術，執行需求訪談、規格撰寫、功能開發、系統測試、Hotfix、資料庫調整及 Kubernetes／OCP 部署。透過保單批次處理、照會、高風險控管及自訂分期繳費等功能，我逐步理解保險業務規則，以及功能變更對資料流、相依系統與後續維運的影響。這段經歷讓我體會到，完成程式實作只是開發的一部分，理解需求背後的業務目的，才能做出符合實際使用情境的設計。

於昕力資訊期間，我負責 AI／真人客服產品及客製專案開發。面對多個專案重複實作及前後端責任邊界不清的問題，我主動參與需求釐清，運用 Template Method、Java 泛型及 SOLID 原則設計跨專案共用的 API 呼叫框架，統一核心流程、錯誤處理及紀錄機制，同時保留各專案的擴充彈性。這使我開始更深入思考功能共用的適用範圍：哪些流程值得抽象，哪些差異應保留獨立性，以及如何在重用性、耦合度與維護成本之間取得平衡。

架構、安全性、可觀測性與效能

目前任職鈦創軟體，先後參與富邦人壽行動保全 BFF／MID 及核心系統現代化之借還款專案。行動保全期間，我負責 Java／Spring Boot 微服務開發、既有功能調整及 TWID、OCR 等外部服務整合。延續過去對共用設計與責任邊界的思考，我嘗試將 DDD 導入實際開發，將業務規則封裝於領域層，使主流程聚焦於流程協調（ Orchestration ），並透過 JUnit、Mockito 獨立驗證核心業務邏輯，搭配整合及回歸測試，提升系統可測試性與維護性。

在設計 TWID Callback API 時，我針對暴力請求、快取穿透及跨系統狀態不同步等風險，評估 Bloom Filter、多層快取與請求驗證等方案，最終採用 Request 本身可驗證的密鑰機制搭配 Rate Limit，降低驗證流程對快取狀態的依賴及對外 API 遭濫用的風險。這次經驗讓我更重視技術選型背後的適用條件、風險及⻑期影響，而非單純追求技術本身的複雜度。

為改善系統問題的追蹤與定位，我運用 Spring AOP、MDC、Kafka、Queue 與 Batch Insert 設計非同步結構化 Log 流程，兼顧 Request 關聯追蹤、錯誤定位及降低同步寫入負擔，並研究跨執行緒 MDC 資訊傳遞的策略與限制。同時參與 Redis Sentinel／Cluster 高可用架構驗證，透過 JMeter 模擬壓力與 Failover 情境，觀察節點切換、Client 重新連線及服務可用性，理解分散式系統在異常狀態下的實際行為。

處理系統異常與效能問題時，我曾透過 Oracle SQL 執行計畫分析索引與查詢效能，並排查 HikariCP Connection Leak、記憶體及系統資源異常。我習慣先蒐集紀錄與監控指標，結合問題重現、壓力測試及執行環境觀察定位瓶頸，再驗證改善效果與變更影響範圍。這些經驗逐步建立了我以實際證據進行技術判斷的習慣，也促使我思考如何將個人的開發經驗轉化為團隊可採用的設計原則與開發策略。

技術領導與專案治理

近期轉入借還款專案後，我開始承擔整體架構規劃與技術領導職責，有機會將過去的大型工程整合、系統設計及開發策略思維應用於專案層級。加入專案初期 2–3 週內，我主動盤點業務流程、功能相依性、既有架構及工程管理機制，辨識改善方向，從開發策略、資源配置、功能優先順序、交付進度及敏捷開發等面向制定改善方案，並向主管說明執行方式與預期效益，取得對專案推動策略的認可。

確立改善方向後，我結合 DDD／BDD 的領域建模與業務行為分析思維，進行功能分類、模組拆解及共用策略規劃。對於業務語意一致且具共用價值的功能進行整合，可能因業務規則而產生不同演進方向的功能則保留獨立性，避免為了重用而增加不必要的抽象與耦合。同時釐清 BFF、核心業務服務及中台對外 API 三大架構區塊的職責與介接邊界，透過介面抽象、依賴反轉及職責隔離，區分流程協調、領域邏輯、業務規則檢核與基礎設施實作。

架構設計的價值在於團隊能否真正落實，因此我主持跨團隊架構會議，制定開發規範、實作範例及模組整合策略，向外包團隊說明設計概念、指導實作並協調技術問題。為使開發與整合進度更容易掌握，我也推動以 Jira 工單取代既有 Excel 人工追蹤方式，依業務模組與功能進行工作拆解、任務分組及每週交付目標設定，透過定期會議追蹤實作進度、技術問題及整合需求，逐步建立具備明確責任邊界與可追蹤交付機制的開發模式。

除了交付進度，我也關注資源投入與實際產出之間的關係，建立會議工時及人力投入統計機制，將例行會議、技術討論及進度呈報納入每月資源控管，作為後續人力配置、管理成本及開發效率分析的依據。

工程生產力與成本最佳化

隨著 AI 改變軟體開發方式，我進一步思考如何依任務複雜度、重複性及業務價值，合理配置工程人力、AI 與自動化工具。針對具有固定規則的基礎實作，目前正規劃可跨模組重用的 DB Mapping 與模板化程式碼生成機制，讓重複性工作由確定性自動化處理，差異化功能、測試及重構則由 AI 輔助，使工程師能專注於業務理解、領域建模、架構決策及品質驗證。我期望在維持工程品質與實作一致性的前提下，減少重複開發工時與 AI 使用成本，提升整體團隊的工程生產力與交付效率。

AI 協作工程理念

這套開發策略也延續了我平時運用 AI 的工程理念。我重視由工程師主導需求、架構及品質決策，透過明確規格、模組邊界、API Contract 與驗收條件引導 AI 進行需求拆解、實作、測試及重構，並結合 Code Review、自動化測試及 CI/CD 驗證產出。測試聚焦於業務規則、邊界條件與異常情境，讓效率提升建立在可驗證的品質上，兼顧安全性、可維護性及技術債控制。

自主學習與技術成長

工作之外，我持續透過 AI 互動學習、Udemy 線上課程、技術文件及年度研討會深化能力，範圍涵蓋雲端與容器部署、Spring 生態系、Redis、Kafka、設計模式、資料結構與演算法、JVM／GC 及 AI Agent 開發。我習慣建立獨立環境，透過實作、部署、壓力測試及故障模擬理解技術原理、適用場景與限制，再評估如何應用於正式專案。

個人專案與技術驗證

目前主要開發 My Mobile Secretary 個人 AI 助理平台，以 Java／Spring Boot 建立模組化系統，分離 AI Dispatcher 與核心業務邏輯，透過明確的 Contract、Intent Understanding 與 Test Harness，探索 AI Agent 與既有後端的安全及可測試整合。AI 負責語意理解、意圖判斷與流程協調，重要業務規則及狀態異動仍由 Java 控制。這個專案讓我能持續驗證領域邊界、規則封裝及 AI 協作開發方法。

我也建立 QPS-tuning、Java-gRPC、JFR／JMC 及 HTTP Range Streaming 等實驗專案，研究限流、Redis 故障切換、JVM GC、執行緒競爭與高負載下的系統行為，搭配 JMeter、Micrometer、Prometheus 及 Grafana，觀察延遲、吞吐量、錯誤率及資源使用情形，分析瓶頸與系統失效原因，並透過測試及監控驗證改善效果。

工程信念與未來方向

回顧從大型建築工程整合、軟體開發到近期承擔專案領導職責的歷程，我的關注重點逐漸由個人開發品質延伸至整體系統品質與團隊交付能力。未來，我希望持續深化企業核心系統、領域知識、分散式架構及 AI 協作工程能力，結合過去大型工程整合經驗與近期的專案治理實務，朝 Project Lead 方向發展，在持續參與技術設計與實作的同時，制定合理的技術與執行策略、整合團隊能力、推動工程改善，並對系統品質與專案交付成果承擔責任。

Professional background & cross-disciplinary work

I am a software engineer with about four years of Java development experience, focused on backend systems, with experience in React, Redux, JavaScript, and JSP. I have worked on insurance core systems, AI and live customer service products, and enterprise microservices. My focus has expanded from feature development to system architecture, technical decisions, and engineering quality. Recently, I have taken on technical leadership, engineering governance, and project delivery responsibilities on a core system modernization project for Fubon Life Insurance.

Before entering software development, I spent about eight years in architectural design and large construction projects, including Taoyuan International Airport Terminal 3. I coordinated design interfaces across architectural, structural, mechanical, and electrical teams. Using Dynamo and Python to automate BIM data processing sparked my interest in programming. After completing Java training at Tibame, I changed careers. I now draw on this experience in system planning, dependency analysis, and cross-team coordination.

Enterprise development & system design

I began my software career developing insurance core systems with Java, Spring Boot, Spring Cloud, Spring Batch, Oracle Database, React, and Redux. My work covered requirements, specifications, development, testing, hotfixes, database changes, and Kubernetes/OCP deployment. Policy batch processing, inquiry workflows, high-risk controls, and installment payment functions taught me how business rules and feature changes affect data flows, dependent systems, and maintenance.

At TPI, I developed AI and live customer service products and customized solutions. To address repeated development work and unclear frontend/backend responsibilities, I designed a shared API integration framework using the Template Method pattern, Java generics, and SOLID principles. I standardized common flows, error handling, and logging while allowing project-specific extensions. I learned to balance code reuse, coupling, and maintenance costs.

Architecture, security, observability & performance

In my current role, I have worked on Fubon Life Insurance’s mobile policy servicing BFF/MID and loan and repayment modernization projects. For mobile policy servicing, I developed Java/Spring Boot microservices, integrated TWID and OCR, and applied Domain-Driven Design (DDD) to separate business rules from workflow orchestration. I used JUnit and Mockito to test core business logic independently, along with integration and regression tests.

When designing the TWID Callback API, I analyzed abusive requests, cache penetration, and inconsistent states across systems. I evaluated Bloom filters, multi-level caching, and request verification before adopting secret-key-based request verification with rate limiting. The design reduced dependence on cached state and helped protect the public-facing API. I learned to consider technical trade-offs, risks, and long-term impact.

To improve troubleshooting, I designed asynchronous structured logging with Spring AOP, MDC, Kafka, queues, and batch inserts to support request tracing and reduce synchronous write load. I also studied cross-thread MDC propagation and participated in Redis Sentinel/Cluster high-availability testing with JMeter to observe failover, client reconnection, and service availability under load.

When dealing with performance issues, I used Oracle SQL execution plans to analyze indexes and queries and handled HikariCP connection leaks, memory problems, and resource issues. I collect logs and metrics, reproduce problems, and use load tests to locate bottlenecks and verify changes. This taught me to make decisions based on evidence and consider how to turn individual practices into team standards.

Technical leadership & project governance

After joining the loan and repayment project, I began taking on technical leadership responsibilities. Within the first two to three weeks, I reviewed business processes, dependencies, architecture, and development practices. My improvement plan covered development strategies, resource allocation, priorities, delivery schedules, and Agile practices. I gained management support for the proposed strategy and began putting it into practice.

I then applied DDD and Behavior-Driven Development (BDD) principles to analyze business behavior and define module boundaries. I identified which functions could be shared and which should remain independent based on business rules and future needs, avoiding unnecessary abstraction and coupling. I defined responsibilities across the BFF, core business services, and shared platform APIs. Through interface abstraction and dependency inversion, I separated workflow coordination, domain logic, business rule validation, and infrastructure implementation.

A good architecture needs to work in practice. I lead cross-team architecture meetings, define development standards, provide implementation examples, and guide external development teams. I am moving the project from manual Excel tracking to Jira-based task management. I organize tasks by business modules and functions, set weekly delivery goals, and track progress, technical issues, and integration needs.

Beyond delivery schedules, I track staff time spent on meetings, technical discussions, and progress reporting. These records provide a basis for monthly resource management, cost analysis, and development efficiency reviews.

Engineering productivity & cost optimization

To improve engineering productivity, I am planning how to allocate human, AI, and automation resources based on task complexity, repetition, and business value. For repetitive tasks with fixed rules, I plan to use reusable templates to generate database mapping and infrastructure code across modules. AI would assist with feature development, testing, and refactoring, while engineers would focus on higher-value work such as business analysis, domain modeling, architecture decisions, and quality validation. This strategy aims to reduce development time and AI costs while maintaining code consistency and improving engineering productivity and team delivery.

AI-assisted engineering practices

This approach builds on my AI-assisted engineering practices. I define requirements, module boundaries, API contracts, and acceptance criteria to guide AI. I use code reviews, automated tests, and CI/CD to validate AI output, focusing on business rules, edge cases, and failure behavior while managing security risks and technical debt.

Self-learning & technical growth
